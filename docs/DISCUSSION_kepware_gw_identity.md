# 討論記錄：KIS → Kepware API Gateway 身分傳遞

> 狀態：**討論中，尚未決定實作方向**。本文件只記錄討論脈絡與待決策點，
> 未經使用者明確拍板前不要依此實作。

## 觸發背景

2026-07 排查同事的建點程式撞到 Kepware API Gateway 429 限速時發現的隱性問題：
KIS 呼叫 Kepware Gateway 目前一律使用 `kepware_gateway` 表中儲存的**單一服務帳號**登入
（`_resolve_gw_credentials` → `KepwareGatewayClient.login()`），不論實際操作者是誰。
這代表當初在 GW 端設計「個人帳號」想達到的效果，在 KIS → GW 這一跳被抹平了。

同一事件也暴露：GW 端限速是「帳號＋路徑」滑動視窗，所有 KIS 使用者/呼叫端共用同一個額度桶。

## 已確認的需求（使用者回覆）

1. **當初設計個人帳號的目的**：權限卡控 + 稽核，兩者都要（非單一目的）
2. **GW 端帳號權限**：目前**已經**有實際分級（不同帳號能做的事不同）
3. **規模與情境**：
   - 實際會操作建點的人數 **< 10 人**
   - GW 端另外還有**回寫 Kepware** 的既有需求/客戶端
   - 觸發本次事件的根因：同事想開發一個 **Agent** 自動執行建點流程，
     即現有服務帳號模型下一定會出現「機器身分」的需求

## 已評估的方案

### A. 維持服務帳號 + 身分透傳標頭（成本最低）
KIS 後端打 GW 的每個請求加自訂標頭（如 `X-On-Behalf-Of: <KIS username>`），
GW 端 middleware 記進稽核 log，甚至可用它取代「帳號」作為限速 key。
- 優點：改動最小，密碼管理維持一份
- 缺點：GW 端「按帳號分權限」做不到（權限判斷仍全部留在 KIS 這邊），
  且 GW 必須信任來自 KIS 伺服器的 header 內容

### B. 每人一組 GW 帳號，存在 KIS（user × gateway 憑證表）
- 優點：GW 端稽核/權限/限速額度完全反映到個人
- 缺點：憑證生命週期成本高（N 人 × M Gateway 都要開帳號、輪換密碼）

### C. Session 期間代登入（不落地密碼）— 不建議
背景任務動輒跑幾十分鐘，GW token 中途過期需要密碼才能重登，
與「不落地密碼」的初衷直接衝突，實務上最麻煩。

### 串 AD — 適合做，但只解決一半
- 解決：密碼不落地兩套系統、到職離職 IT 統一管、AD 群組對映角色
- **解決不了**：KIS 代替使用者呼叫 GW 那一跳的委派問題
  （AD bind 驗證即丟，KIS 拿不到、也不該存 AD 密碼）
- 機器身分（Agent）不該掛在個人 AD 帳號下

### KIS ↔ GW 帳號同步 — 不建議做「密碼同步」
若要讓 KIS 用使用者本人帳號登入 GW，KIS 必須持有可逆加密的明文密碼，
等於自建半套身分供應商，10 人以下規模不划算。
（若只做「帳號開通同步」，成本較低，但委派問題依然沒解。）

## 目前傾向的方向（尚未拍板）

**Token 信任**：KIS 簽發帶身分的 JWT（`sub=使用者`），呼叫 GW 時帶這張 token
而非服務帳號密碼登入；GW 信任 KIS 作為 issuer，驗簽後照 `sub` 查自己既有的權限表卡控。
同時解決權限卡控、稽核、Agent 身分（服務帳號/API key）、限速額度隔離、
以及背景任務 token 過期問題（KIS 可在任務內用自己的簽發權重簽）。
AD 建議放在此架構外層，之後視 IT 配合度再做（人類登入從本地密碼換 LDAP bind，其他不動）。

## 待決策點（尚未確認）

1. GW 端既有「回寫 Kepware」的其他客戶端，要繼續用 GW 自己的帳密登入，
   還是也收編進同一個 issuer？（可以並存，GW 同時接受兩種 token 來源）
2. HS256 共用密鑰 vs RS256 非對稱金鑰——是否在意「GW 理論上能偽造 KIS token」
   這件事（HS256 兩邊都拿得到同一把密鑰；RS256 則 GW 只持公鑰、無法偽造，
   但金鑰管理稍複雜）？

## 2026-07-14 補充討論：現況（服務帳號）的稽核可行性

使用者提出：**就算 GW 端目前看到的都是同一個服務帳號，稽核不算完全失效**——
因為 KIS 這邊 `activity_log` 已經記錄「誰、什麼時間、做了什麼動作」
（`execute_tb` / `execute_scale` / `kw_delete` 等，含 username + timestamp + ip），
只要 GW 端自己的存取 log 也有時間戳記，兩邊**用時間對照**就能反推出
「這個時間點透過 API 建點/改動的是 KIS 的哪個使用者」。

也就是說，**稽核需求在目前架構下並非完全空白**，只是從「GW log 直接看到操作者」
降級為「KIS log + GW log 跨系統時間比對」的間接稽核，且仰賴：
- KIS 與 GW 兩邊系統時間同步（否則時間比對會有誤差）
- 若同一時間窗內有多個 KIS 使用者同時操作同一 Gateway，時間比對會有模糊地帶
  （無法精確歸屬到單一使用者，只能縮小範圍）

這個補充**不影響上面「權限卡控」需求依然無解**的結論（權限卡控需要 GW 端
即時知道是誰在請求以決定能不能做，事後時間比對幫不上忙），
但代表「Token 信任」方案的急迫性，主要壓力來自**權限卡控 + Agent 身分**，
稽核本身用現有 KIS activity_log + 時間比對可以先撐著，不是完全阻斷。
